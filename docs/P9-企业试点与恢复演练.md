# P9 企业试点与恢复演练

## Agent 和执行服务边界

Agent 在独立进程中运行锁定的 LiteLLM 模型适配，接收执行服务按发布策略裁剪的上下文。请求通过私有 Unix 套接字传递，仅包含模型绑定摘要、上下文与期限。数据库、签名、源系统和证据存储的凭据保留在各自专用服务。执行服务复核 Agent 返回的动作、引用和用量，继续执行现有租户预算、审批与 OpenWorkProof 授权流程。原模型绑定和发布摘要在切换传输时保持稳定。

在同一主机的两个容器之间共享私有套接字卷。Agent 使用模型侧网络，执行服务使用业务侧网络，分别挂载自己的配置和凭据。Agent 端持有模型凭据。执行服务使用 `--agent-socket` 和程序调用同一个套接字，套接字故障按模型调用故障处理。已有嵌入接口仍由其授权服务处理。

```bash
python -B -m ai_native_system.agent_process --socket /run/ai-native-agent/agent.sock --models "$agent_model_config"
python -B -m ai_native_system --postgres --registry "$registry" --models "$models" \
  --tools-config "$tool_config" --agent-socket /run/ai-native-agent/agent.sock serve
```

套接字目录由部署方预先创建为专用身份所有，目录权限 `0700`，套接字权限 `0600`。使用独立容器时，为两个容器的套接字访问设置一致的数字 UID，只共享套接字卷。Agent 侧启用只读根文件系统、降权和资源限制，允许访问指定模型端点。执行服务侧按连接器放行查询和写入目的地。

同一主机的 Compose 基础配置见 [`deployment/isolation/compose.yaml`](../deployment/isolation/compose.yaml)。用 `python -B deployment/isolation/verify.py --build-image IMAGE` 构建最小 Agent 镜像。设置 `AI_NATIVE_ISOLATION_IMAGE`、`AI_NATIVE_ISOLATION_AGENT_CONFIG` 和 `AI_NATIVE_ISOLATION_AGENT_ENV_FILE`，分别指向镜像、Agent 的受信模型配置及只含模型凭据的环境文件。将已批准的模型网关接到 `model` 网络。可信执行服务用同一 Compose 项目的只读挂载 `agent_socket:/run/agent:ro`，以 UID/GID `65532` 使用 `--agent-socket /run/agent/proposal.sock`，接入独立的业务侧网络。Agent 网络不接入业务侧出口。执行服务按现有配置获取业务凭据，Agent 镜像仅包含模型侧代码。

运行中的任务固定原发布版本。模型配置更换时，Agent 可用多个 `--models FILE` 同时加载现用及仍有任务依赖的历史模型配置，保留各版本的供应商允许范围与模型绑定摘要。Compose 基础配置默认挂载一个模型文件，需要保留历史路由时，额外挂载对应的模型配置并传入参数。在正式环境对模型凭据设置供应商侧配额，并对照来源账单核对用量。

## Ontology 权威只读查询

企业入口 `POST /v1/query` 或 SDK `Client.query` 使用 `authoritative` 选项打开权威详情。调用方提供应用、对象类型和规范 ID。详情随该应用当前选定发布解析。控制台「事实核查」填写应用标识后使用此模式，单字段状态入口继续可用。下例使用通用验收配置的命名，字段和关系应以试点发布为准。

```json
{
  "application": "single",
  "object_type": "asset",
  "object_id": "asset-1",
  "authoritative": {"fields": ["$state", "checksum_ok"], "preview": true}
}
```

可选 `relation` 接一个已发布的关系名。每次限定一个对象、最多 16 个字段、一个关系与最多 200 个可见关系成员，有三秒总查询预算与 256 KiB 响应上限。对象确认已删除时停止展示，即使另一来源仍保留字段。按对象、字段、状态、边和目标对象读取权限展示。可单独配置 `read provenance <规范对象 ID> <字段或关系名>` 查看来源元数据。字段返回来源及源版本、新鲜度和覆盖。关系覆盖只描述获准子集的权威读取，成员数始终是可见成员数。未取得展示规则所需权限或关系依赖范围无法确定时，返回统一的 `not_displayable`。

预览复用 Runtime 的确定性规则求值。查看预览需要动作的 `read / action / 动作ID` 和独立 `preview / action / 动作ID`，并继续校验应用、发布、对象、字段及关系权限。获准后可见三态条件、规则版本及声明中的目标状态。预览执行零写入、零模型和工具调用。实际审批与执行继续使用当前读取集、OpenWorkProof 和源端条件核验。

```bash
python -m ai_native_system --postgres --tenant "$tenant" govern grant "$principal" preview action "$action_id"
```

委派调用时，同时给两个已获准主体配置对应的精确授权，并在委派中包含 `["preview", "action", "动作ID", null]`。现有授权命令和 JSON 结构继续适用。工具执行授权与动作发现沿用现有入口。

`python -B deployment/local-postgres/verify_p2b.py --only authoritative` 使用一次性真实 PostgreSQL 复跑。十二项端到端用例覆盖权威字段与关系、旧查询、独立预览授权、依赖与委派撤权、制度手动切换和零执行副作用。制度切换用相同参考事实核对选版与规则判断变化。真实企业对象、映射与业务判定样本待接入。

### 试点制度切换

由业务负责人在试点登记单确认制度条款及版本、生效和失效时间与时区、指标口径、发布摘要、切换人、执行截止依据和在途审批处置。先保留新发布草稿并完成规则绑定与样本对照。到切换窗口时，使用独立发布角色发布并选用新版本，再按已确认策略弃用或撤销旧发布。弃用停止新任务，允许已固定旧发布的任务继续按原审批复验。撤销阻止尚未派发的旧任务推进。默认选版变更后仍须处理旧发布状态，因为已发布的旧摘要仍可被显式请求。

通过现有分步控制入口切换时，暂停相关任务提交和新写入，直至核对选版、发布状态和授权结果。已派发或结果未知的操作沿原操作 ID 查询。若业务要求以源端提交时点为严格界线，需提前排空，或在指定源以授权到期时点校验并实测拒绝。当前生效时间由业务方和发布运维按登记窗口控制，自动硬截止及真实制度交界仍待试点验证。

## 索引读取授权

知识查询按实际选择的索引版本检查 `read / knowledge-index / 索引ID`。用户和服务使用授权后的现有 API、SDK 和 CLI。既有配置结构、索引数据、应用发布及证据格式继续适用。由治理角色为获准读者、引用型任务的请求者、执行者、审批者以及获准服务按实际使用补齐索引授权。活动索引与仍被引用的退役索引分别核对。

```bash
python -m ai_native_system --postgres --tenant "$tenant" govern grant "$principal" read knowledge-index "$index_id"
```

委派需要两个主体的授权和精确 scope `["read", "knowledge-index", "索引ID", null]`。现有委派如缺相应 scope，签发调整后的委派并按现有规则撤销旧委派。对未授权的显式索引统一拒绝，存在性仅在通过授权后校验。通过索引授权后继续校验文档、委派、当前版本和撤回。缺索引授权时在向 embedding 服务发送查询前拒绝，模型输出和正文出站前复核当前授权。

退役索引中的固定引用按原索引、文档版本、片段位置和内容摘要复核。现场收紧索引权限前先核对在途任务涉及的主体和索引。主动撤销后，相关内容会从检索、记忆和证据读取中失去可见性，待执行任务按既有审批链路复验。已持久的审计记录沿原权限查阅。

在真实 PostgreSQL 18.7、pgvector 0.8.7 和迁移 `0020_application_delivery` 上，`python -B deployment/local-postgres/verify_p7.py` 共 33 项通过。索引专项 8 项覆盖默认和显式读取、委派、调用期间撤权与退役索引。应用测试确认撤权后零 embedding 和生成请求。已签名的在途任务在执行者失去原索引权限后被阻断，业务效果、授权消费和证据增量均为零。

## 中文混合检索

运行 `migrate` 应用 `0021_knowledge_lexical`。迁移为已有向量片段回填词法倒排索引，后续词项随片段事务维护。已有文档可以直接检索，无需再次分段或调用 embedding。仅给启用混合模式的可信检索数据库角色授予 `SELECT ON ai_native.knowledge_lexical_postings`。业务用户和委派继续通过实际索引读取授权与文档授权校验。

```bash
python -m ai_native_system --postgres migrate
python -m ai_native_system --postgres --tenant "$tenant" --models "$models" \
  p7 search '“保留审批记录”' --method hybrid --actor "$actor"
```

CLI 用 `--method hybrid` 启用。未固定检索绑定的问答或产物应用跟随租户活动索引，可在应用目录的对应条目设置 `"retrieval_method": "hybrid"`。默认使用精确向量检索。固定绑定见下节。

普通关键词用中文词组召回和 pgvector 候选一起排序。单独输入 `第2条` 时按完整条号匹配，支持常用中文数字和全角数字。带引号的短语须在同一片段连续出现。条款号或引号短语没有获准的精确匹配时返回空结果。两路共用当前文档、委派、撤回约束，返回片段时再次校验权限和原文引用。

混合模式每路最多取 100 个候选。可用 HNSW 时先用近似索引，候选不足时尝试有界精确检索。获准集合超过精确检索预算时，保留已有向量候选和词法候选，并在检索结果中记录 `exact_candidate_limit`。只有词法候选可用时，实际方法记为 `lexical`。真实语料的检索质量、文档覆盖、无答案门槛和性能待试点评测。

## 发布固定检索索引与回滚

问答和产物应用可在发布草稿固定知识索引、检索方法及索引绑定的 embedding 摘要。它们随发布快照一起计算摘要。可以选择 `exact`、`hnsw` 或 `hybrid`。含固定配置的发布按指定索引执行，历史应用发布继续沿用原快照和目录配置。

```bash
python -m ai_native_system --postgres migrate
python -m ai_native_system --postgres --tenant "$tenant" --registry "$registry" --models "$models" \
  release draft "$application" --actor "$operator" --knowledge-index "$index_version" --retrieval-method hybrid
python -m ai_native_system --postgres --tenant "$tenant" --models "$models" \
  release publish "$release_digest" --actor "$operator"
python -m ai_native_system --postgres --tenant "$tenant" --models "$models" \
  release select "$application" "$release_digest" --actor "$operator"
```

控制角色沿用现有发布和身份相关权限，并增加对 `knowledge_vector_spaces`、`knowledge_sources`、`knowledge`、`knowledge_vector_documents`、`knowledge_vector_chunks`、`fact_invalidation_outbox` 的 SELECT。操作主体须具备目标索引的 `read / knowledge-index`。通过发布 API 操作还须具备应用的 `manage / app`。应用用户仍须具备实际索引和文档读取权限。发布和选择验证索引状态、embedding 配置与声明文档在当前版本的完整覆盖。显式固定 HNSW 时还要校验相应向量索引已构建。撤回和删除沿用当前生效规则。

回滚使用同一个 `release select` 命令切回仍已发布的快照。若目标旧索引缺当前文档，先用 `p7 rebuild INDEX DOCUMENT --actor ACTOR` 补入当前有效版本，再重试选择。重建可为退役索引补齐片段，租户活动索引和源文档版本仍由各自流程管理。移动应用发布指针时，事务内记录旧摘要、新摘要、操作者和时间。审计角色可获准读取 `application_release_selection_history`。在途任务和原文引用继续沿用各自固定的发布与引用，并按当前授权复验。

实测使用 PostgreSQL 18.7、pgvector 0.8.7 和 `0022_knowledge_release_selection`。P8 应用 5 项、P2a 发布 5 项、P7 知识回归 40 项、迁移 7 项、备份恢复 1 项通过。应用测试走真实发布 API，覆盖固定策略、活动索引和目录配置变化、旧索引补齐后回滚、模型范围失配、撤权和撤回。发布测试还覆盖审计记录不可修改、同一选择重试以及跨租户隔离。

## 企业恢复顺序

1. 停止新写入并隔离旧主库，保留源端查询、授权撤销和可验证证据的独立渠道。记录数据库切点、源码发布和工具版本。
2. 从指定备份或 WAL 恢复到隔离的目标。在打开入口前校验应用 schema、pgvector、检查点 schema、业务角色和证据存储引用。记录恢复时钟与还原范围。
3. 由可信签名控制面切换恢复纪元。读取独立保留的撤回与撤权记录，先向恢复库重放，再启动业务读取和新动作。通过 `p7 reapply-tombstone` 应用受控的知识撤回记录。
4. 对已经派发或结果未知的操作，沿原操作 ID 查询源端回执并验证签名。在保留窗口内逐项核对证据摘要、授权消费和业务结果。恢复的图检查点以当前业务状态为准。
5. 用独立源查询确认当前对象版本、写入计数和源端条件。确认客户端角色、出站地址、观测和告警配置后，根据试点方确认的恢复目标开放后续流量。

指定环境还需验证跨主机网络隔离与出口策略、受信 TLS 和密钥托管、自动故障判断与旧主隔离、计划复位与备库重建、WAL 时间点恢复、长运行续租、生产负载、告警和应急停用。Temporal 与 OpenFGA 由试点对持续调度和复杂授权的需求决定。

### 正式试点配置清单
