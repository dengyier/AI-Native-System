后续同日已完成 [六层深入审查](六层架构深入审查-2026-11-16.md)，新增 24 个细化条目并复跑现有 59 项测试、定位 6 条连接告警。本文件保留第一轮状态与主题编号；最新证据和逐项方案以深入记录及开发计划第 6 节为准。

关联：[目标架构](六层系统架构与复用方案-OpenWorkProof.md) · [开发与验收计划](superpowers/plans/2026-11-16-six-layer-owp-integration.md) · [已实现与待完成清单](六层能力核对.md)。

## 1. 审查结论与证据边界

当前框架具备通用类型/动作配置、顺序 Agent 阶段、版本复验、审批与本地/远端单动作恢复基础。Ontology 尚是基础类型、单目标关系和简单前置条件；不能把它记作完整的企业语义服务。事实版本不等于事实历史，配置摘要不等于不可变发布材料，工具回执也不自动证明所有业务前置事实真实且新鲜。

本次将这三个缺口补进同一条依赖链：本体与事实契约 → PG 持久化 → 身份/语义权限/发布 → 事实同步与规则 → OWP 语义授权 → 源侧条件执行与回执核对。仅接入 OWP 签名不能补足这条链。

59 项通过是前次 SQLite/本地合成环境测试结果，不是本次新增能力的结果。本轮观察来自下列源码入口及现有设计；未运行利用验证的风险不表述为已证实的漏洞。新增能力的状态统一为“设计已补，待实现与验收”。

优先级：“前置”表示后续能力依赖其成立；“集成前”表示对应组件开放前必须完成；“部署前”表示必须在指定企业环境证明。它们不是漏洞严重等级。

## 2. 第一层：基础设施

已实现：SQLite 持久事务、唯一约束、任务和远端操作记录。主要证据：[storage.py](../ai_native_system/storage.py) 的 `SCHEMA`、`database`，以及 [runtime.py](../ai_native_system/runtime.py) 的任务领取逻辑。

| 编号 / 优先级 | 源码观察与缺口 | 修订方案 / 阶段 | 验收证据 |
| --- | --- | --- | --- |
| L1-01 / 前置 | `database` 使用 SQLite 事务；DDL、占位符、`rowid` 和 JSON 字符串约定绑定当前后端。PG 尚未接入，不能仅换连接地址 | P1a 先固定语义，P1b 迁移数据、事务与并发行为；保留旧操作 ID、摘要和审批，不补造事实历史 | V01：旧库迁入 PG 后 ID/摘要/待对账状态不变，多连接竞争只领取一次，中断迁移可恢复 |
| L1-02 / 前置及部署前 | 当前可信本地进程边界尚无 PG RLS、执行进程隔离或主备一致性保证；`tools.register` 接受可信 Python handler，不是安全沙箱 | P2a 受限账号/RLS；P3 一致性授权读取；P9 秘密/网络/执行隔离及恢复演练 | V02：池连接切租户不泄漏、滞后副本不作授权决定；部署演练中 Agent 不能读取业务凭据，恢复后不重放效果 |

结论：继续复用 PostgreSQL/pgvector 和部署设施；自研限于持久化适配及业务一致性契约。数据库、源系统、证据存储恢复到不同进度时，先核对再恢复写入。

## 3. 第二层：数据与 Ontology

已实现：[registry.py](../ai_native_system/registry.py) 的 `_validate_types`、`_action`、`validate_object` 校验类型/状态/属性/单目标关系；[data.py](../ai_native_system/data.py) 的 `put_object` 校验版本和同租户关系，替换当前对象；知识有单独历史。

| 编号 / 优先级 | 源码观察与缺口 | 修订方案 / 阶段 | 验收证据 |
| --- | --- | --- | --- |
| L2-01 / 前置 | 属性目前是基础类型，关系值为单个 ID，动作规则是属性相等/关联状态条件；缺单位、基数、关系时间、规则解释、语义查询和本体生命周期 | P1a 元模型与领域包；P2a 查询和发布；P2b 有界规则及读取集；P8 管理界面 | V03：两个领域配置共用核心；多对多/单位/空值正确；关系聚合、发布影响、规则三值结果可解释 |
| L2-02 / 前置 | `put_object` 更新当前投影；没有来源身份映射、事实双时间历史、字段权威、源进度、冲突或删除同步 | P1b 事实存储；P2b 双源接入、去重/乱序/历史/新鲜度/墓碑；P7 接证据及检索失效 | V04：同名异物不合并，重复/乱序不覆盖新事实，崩溃恢复不丢投影事件，源冲突/不完整依据不能误判可执行 |

Ontology 的首期边界：类型、属性、关系、状态、规则、动作、事件和发布；查询以有限遍历与受限聚合为主。暂不建设完整 OWL 推理、任意规则脚本或独立图数据库。PG 保存结构化语义与事实，pgvector 只承担向量检索。PROV/SHACL 可参考来源和约束表达，采用参考语义不等于已实现这些标准。

定义、实例和证据必须分开：本体定义“何种对象/关系合法”；来源断言记录“哪个源在何时声称什么”；事实投影按明确策略形成当前视图；文档片段支持断言；模型抽取首先是候选。可信签名能验证材料来源和完整性，不能替代事实源质量判断。

## 4. 第三层：模型

已实现：[gateway.py](../ai_native_system/gateway.py) 的 `propose` 提供具名路由、开关、上下文大小限制与回退；[model.py](../ai_native_system/model.py) 提供结构化候选和证据约束。

| 编号 / 优先级 | 源码观察与缺口 | 修订方案 / 阶段 | 验收证据 |
| --- | --- | --- | --- |
| L3-01 / 集成前 | 路由 enabled 不等于允许接收本次数据；尚无 embedding 接口或向量空间版本契约 | P5 LiteLLM 适配加供应商/字段权限、允许回退、embedding 模型/维度；P7 固定向量空间 | V05：主模型失败时禁止向不获准供应商回退；向量维度/模型不匹配拒绝发布，受限字段不进入请求和 trace |
| L3-02 / 集成前 | `runtime.metrics` 统计已完成事件的用量；不能据此得出全部供应商尝试费用。`work` 是单租户有限扫描，不具备企业队列公平性保证 | P5 实际尝试、预留/结算、租户配额；P6 有限队列、公平领取、取消与迟到处理 | V06：重试和回退计入真实尝试；未知消耗不当零；并行子任务不突破预算，繁忙租户不阻塞其他租户 |

结论：复用调用和观测组件，保留框架对数据外发、预算与版本的决定权。模型提议不能发布本体、确立权威事实或扩大工具权限。

## 5. 第四层：AI 平台核心与 Runtime

已实现：[runtime.py](../ai_native_system/runtime.py) 的 `_ground`、`decide`、`_execute` 绑定当前定义、对象/关系/知识上下文与审批；[remote_execution.py](../ai_native_system/remote_execution.py) 持久化意图、检查目标/参数摘要、处理未知结果与投影冲突。这些已有检查应保留。

| 编号 / 优先级 | 源码观察与缺口 | 修订方案 / 阶段 | 验收证据 |
| --- | --- | --- | --- |
| L4-01 / 前置 | 当前上下文摘要覆盖已支持的对象/关联/知识，但无通用语义读取集、集合成员变化、新鲜度及 OWP profile；远端发出前本地复验不能锁住外部事实 | P3 绑定本体/规则/来源/字段范围及读取集；P4 源侧原子条件执行或有界预留；无相应保证则限制动作 | V07：审批后仅新增关联成员、改变规则适用版本或撤回依据也拒绝旧授权；复验到远端写入间改变源版本时效果为零 |
| L4-02 / 集成前 | 远端 `operation_id=task_id`；成功回执限定状态变更及版本 +1。尚不能表达一般产物、多步部分成功及补偿，MCP SDK/OWP 尚未集成 | P1a 分离任务/动作/操作/尝试 ID；P3/P4 证据补发、通用回执和部分成功；P6 图恢复只复用既有操作 | V08：首步成功次步失败分别可见；补偿需新授权；签名服务故障和节点恢复不引起再次写入 |

OWP 授权材料必须同时回答：谁、通过何种委派、使用哪份本体/规则、依据哪些来源事实、能读写哪些字段/关系、对哪个规范对象、执行哪些参数、发往哪个工具和目的地、何时失效。实际回执再关联同一授权与操作。

关系集合与聚合尤其需要防漏：例如动作依据“所有关联对象均符合条件”，只签已经读取到的对象版本不足以发现后来新增的关联对象。需要绑定查询范围及集合修订，并在执行边界复验；源数据不完整时，“所有”不能被视为已证明。

多源条件没有共同事务时不承诺全局原子性。人工决定可以在明确范围内接受已披露的业务风险，但不能被描述为消除了竞态或替代硬性授权约束。

## 6. 第五层：AI 应用

已实现：CLI、回环 HTTP、单/双阶段配置；[api.py](../ai_native_system/api.py) 的 `dispatch` 要求 application/object_id/request_key，并按请求者/审批角色控制任务访问。

| 编号 / 优先级 | 源码观察与缺口 | 修订方案 / 阶段 | 验收证据 |
| --- | --- | --- | --- |
| L5-01 / 前置及集成前 | 提交入口强制目标对象，应用绑定单个状态变更动作，不能完整表达纯查询/生成；任务完成不等于证据已验证或人工接受 | P1a 通用输入与独立状态；P4 通用结果；P8 三类非行业化配置与 SDK | V09：权限问答、范围内生成、受控对象操作都经同一公共服务，前两者不虚造目标对象 |
| L5-02 / 集成前 | 当前有角色级任务访问，无字段/关系过滤或本体发布管理界面；后续原样展示完整运行记录可能扩大信息可见范围 | P2a 统一语义权限与独立发布权限；P8 审批展示语义/来源/新鲜度，证据导出同权限 | V10：同租户不同角色不能经任务、解释、审批或导出看到受限字段；模型不能发布规则；过期依据清楚提示并阻止旧动作 |

结论：界面后置，但查询、发布和审批的数据契约前置。应用不自行实现事实判断和授权，不用订单/工单等具体行业流程代替通用框架验收。

## 7. 第六层：业务系统接入

已实现：HTTP/MCP 子集适配及本地独立测试服务；[tools.py](../ai_native_system/tools.py) 的 `configured_tools` 要求 `idempotent=true`，登记 execute/lookup；现有回执对账可保留未知结果，不将 `not_found` 自动解释为未执行。

| 编号 / 优先级 | 源码观察与缺口 | 修订方案 / 阶段 | 验收证据 |
| --- | --- | --- | --- |
| L6-01 / 前置及部署前 | 配置中的幂等声明不能证明真实下游行为；没有统一快照/增量/删除/条件写能力契约 | P1a 定义，P2b 双源实测机制，P4 条件写和回执，P9 企业源独立核验 | V11：重复同操作、相同键不同参数、未知结果与源版本竞争按契约处理；能力未知保持未知，不自动开放写入 |
| L6-02 / 集成前及部署前 | 当前回执可更新对象投影，但未接源变更流；未来回执和同步事件可能重复、先后倒置或矛盾，删除也尚未贯穿知识/记忆 | P2b 关联与去重/冲突；P4 写入回流核对；P7 删除/撤回消费者；P9 实际源验证 | V12：回执与事件互换到达顺序仍只记一次效果；源最终值不同可解释；删除后检索/记忆/待执行授权不使用旧依据，历史效果仍保留 |

结论：业务系统拥有其职责范围内的权威状态，框架维护来源清晰的投影；本体帮助映射语义，不能通过统一名称消除真实冲突。一个源可读、可同步、可执行写入是三个不同能力级别。

## 8. 验收安排与关闭规则

V01–V12 是验收场景组编号，不是已存在或已通过的测试。具体拟新增测试文件、步骤与阶段退出条件以开发计划为准。

| 验收组 | 第一轮实施位置 | 后续复验位置 |
| --- | --- | --- |
| V01 | P1b PG/迁移测试 | P9 恢复演练 |
| V02 | P2a 租户隔离、P3 授权一致性 | P9 执行隔离/主备切换 |
| V03 | P1a 定义、P2a 查询发布、P2b 规则 | P8 管理界面 |
| V04 | P2b 双源事实测试 | P7 失效消费者、P9 真实源 |
| V05 | P5 模型及 embedding | P7 向量检索 |
| V06 | P5 预算/并发、P6 图资源边界 | P9 容量实测 |
| V07 | P3 语义绑定、P4 源侧条件执行 | P9 真实条件写 |
| V08 | P4 通用操作/证据 | P6 图恢复、P9 故障演练 |
| V09 | P1a 契约、P8 三应用 | P9 接入验收 |
| V10 | P2a 权限/发布、P8 UI/SDK | P9 企业身份 |
| V11 | P2b 同步、P4 写入协议 | P9 实际连接器 |
| V12 | P2b/P4 回流、P7 失效联动 | P9 真实源 |

M1 必须跑通一条语义安全闭环：两源同步 → 规范对象和关系 → 带来源/版本/新鲜度的查询 → 规则判断 → OWP 授权/必要人工决定 → 源侧条件执行 → 回执 → 同步回流核对。至少注入一次关系集合变更、一次源侧版本竞争和一次成功后断连；各自得到明确拒绝、冲突或恢复结果，不重复业务效果。该闭环使用确定性提议即可，不依赖先集成大模型或向量检索。

M2 再加入 pgvector 片段证据、撤回联动、多 Agent 和界面。M3 才能说明真实企业环境中的身份、隔离、源系统和恢复结果。

每个问题仅在其约定阶段有实现及对应验收证据后关闭；跨阶段问题记录已完成子项与剩余范围。外部组件已有功能、设计完成或本地模块测试通过均不能替代这一步。本次完成的是六层第一轮静态审查及计划修订，L1-01 至 L6-02 均保持待实施验证。
