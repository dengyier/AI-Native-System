## 2. 第一层：基础设施深入审查

### D1-01 测试连接未关闭：已复现，P0 修复

**证据与影响：** 本轮 6 条告警均来自上述测试直接使用 `with sqlite3.connect(...)`。该上下文处理事务，退出时不负责关闭连接；[storage.py](../ai_native_system/storage.py) 的 `database` 则在 `finally` 中关闭连接。不能根据垃圾回收时告警落在 HTTP 解析栈，就归因于 HTTP 或框架连接池。参见 [Python sqlite3 连接上下文说明](https://docs.python.org/3.14/library/sqlite3.html#how-to-use-the-connection-context-manager)。

**调整：** 只在已定位的两个测试文件补显式释放或使用已有连接入口；保持原测试目的和断言，不重写存储层。记录应用与测试的连接归属，PG 池化接入后另验归还和回滚。

**验收：** 同命令再次运行 59 项通过、诊断输出不含未关闭连接或忽略的析构异常；故障路径仍能回滚。不能只关闭告警显示来验收。涉及文件为这两份测试，当前尚未修改。

### D1-02 建表混在运行入口：源码观察与迁移风险，P0/P1b

**证据与影响：** [runtime.py](../ai_native_system/runtime.py) 46–57 行构造时执行 DDL；[data.py](../ai_native_system/data.py) 82–106 行写知识时创建历史表。SQLite 下已有补表兼容测试，但这不能直接迁入“运行账号无 DDL 权限”的 PG 方案，也不能管理多版本服务同时启动。

**调整：** 首先确定项目/驱动/扩展版本；PG 采用独立迁移命令、迁移账号、版本及校验摘要，单一迁移执行者。运行入口只检查可兼容的 Schema 范围，缺表或未知版本不接新写入。应用、框架表、LangGraph 表各自明确迁移归属；扩展升级与应用回滚分别规划。保留旧 SQLite 的明确兼容入口，不要求为它重建整套迁移平台。

**验收：** 两个服务同时启动不执行 DDL；迁移账号可迁移，运行账号 DDL 被拒；半途失败后状态可诊断并按该迁移恢复；旧程序遇到不兼容新 Schema 拒绝写入；迁移前后旧摘要/ID 不变。用 `tests/test_migrations.py` 和 `tests/test_postgres_storage.py` 覆盖。

### D1-03 PG 并发边界不能照搬 SQLite：迁移前置，P1b/P2b/P3/P4

**证据与影响：** SQLite 的 `BEGIN IMMEDIATE` 串行化写事务。[data.py](../ai_native_system/data.py) 先读取版本再执行无版本条件的 upsert；[runtime.py](../ai_native_system/runtime.py) 先读任务状态再更新；[remote_execution.py](../ai_native_system/remote_execution.py) 先判断任务再落回执。这些保证依赖当前事务语义。PG 默认 Read Committed 下，同一事务的连续查询可观察不同提交；仅把对象更新改为条件更新，仍未保护关联事实、集合成员或任务终态。参见 [PG 事务隔离](https://www.postgresql.org/docs/current/transaction-iso.html)。

**调整：** 为提交去重、阶段领取、本地执行、远端派发、回执接收和源同步分别写出状态转换表。以任务/操作行锁或等价条件转换串行化同一实例；对象更新带预期版本；唯一约束作最终防线并定义冲突返回。先确定统一锁顺序和短事务，再实现。

动作读取集采用可验证的版本/范围修订锁协议，所有相关写入路径遵守同一协议；集合修订保护新增/删除成员，不能只锁已存在的行。必要的跨对象不变量使用经过测试的 Serializable 事务及有界重试。隔离级别本身不能证明实时撤权：需定义授权判定与撤销的先后边界，判定后已派发动作按 P4 查询结果，不承诺回滚远端效果。参见 [PG 锁与死锁](https://www.postgresql.org/docs/current/explicit-locking.html)。

**验收：** 同版本两次更新只有一次成功；并发接收同回执只记一个效果，晚到失败不能覆盖成功；审批/撤销/执行两种先后次序均符合已定义边界；在读取后插入关联成员时不能使用未复验的旧集合执行。死锁/序列化失败只重试未发生外部副作用的事务部分。另注入提交后连接断开，先按稳定 ID 查询本地提交结果，不直接重新调用工具。主要文件为 PG 适配、data/runtime/remote_execution；测试进入 PG 存储与语义绑定套件。

### D1-04 租约时钟与过期持有者：已有部分防护，P1b/P5/P6

**证据与影响：** `runtime._plan` 175–185、229–234 行使用 Worker 的 `time()` 计算和验证租约，已有 token 检查和迟到丢弃；当前测试覆盖过期领取及取消迟到。尚未覆盖两个 Worker 时钟偏差、持有者过期后复活、长模型调用续期或主备切换。不能把“单次调用受租约保护”解释为供应商不会重复收费。

**调整：** PG 短事务内用数据库侧时间和条件更新领取/续租，写检查点必须匹配仍有效的领取 token 与阶段。锁等待后也检查真实截止时点，不使用长事务开始时刻替代当前时间。对超过单次租期的调用明确续期策略和任务硬截止；即使续期失败，旧持有者也不得提交。模型网络调用继续在事务外。P1b 建基础；P5/P6 管调用、图节点和预算，Temporal 后引入时接管调度而不重建操作身份。

**验收：** 两进程时钟人为偏移，仍按数据库租约只接受有效持有者结果；A 过期、B 接管、A 晚到时 A 不能覆盖 B；续期中断/取消/重启不重复归还配额；调用可能重复但都计入实际尝试。覆盖数据库重连后旧 token 与过期检查，采用计划中的 PG/图运行测试。

### D1-05 运行账号和租户隔离需要覆盖子表：架构缺口，P1b/P2a/P3

**证据与影响：** 当前对象/任务按 tenant 读取，但 steps/events/effects/operations/claims 主要以 task_id 关联，部分内部查询只有 ID。可信本地进程入口先验证租户，不等于这些表在 PG 下已具备独立的租户防线；向量、事实历史和 outbox 还未建立。

**调整：** P1b 设计每张租户数据表的隔离方式，新增表优先显式 tenant 及复合关联约束；依赖父任务策略的表必须有不可旁路且可测的授权连接。P2a 在受限账号下启用读写策略、事务内身份、池归还回滚与受控 schema 搜索路径；迁移/运行/对账职责分开。禁止运行账号自行提权、改策略或执行整表清空。RLS 不覆盖所有数据库操作，因此它不是授予任意 SQL 的理由。[PG RLS 文档](https://www.postgresql.org/docs/current/ddl-rowsecurity.html)

**验收：** 直接使用运行账号，对父表、所有子表、历史、同步记录和向量逐个尝试跨租户读写/引用，均拒绝；无上下文拒绝；正常提交、回滚、取消后的池复用不残留身份；后台对账只能访问分配范围。返回错误不得暴露另一租户记录是否存在。使用 `tests/test_postgres_tenant_isolation.py`，不是仅验 API 的 happy path。

### D1-06 连接上限、就绪状态与停机语义：架构缺口，P1b/P4/P5/P9

**证据与影响：** SQLite 每次开连接；API 使用 ThreadingHTTPServer；`work` 是有限扫描，不是受监督的持久服务。存在请求体/响应体上限、socket 超时，但没有服务级连接池预算、完整调用期限、排空或依赖就绪契约。MCP 可经过多次请求，单 socket 超时不能视作整次操作期限。

**调整：** P1b 先建立有限数据库连接池、获取/锁/语句/事务空闲超时、基础就绪检查、结构化错误和 Worker 排空。存活只表示进程在运行，就绪需符合该服务所需的 Schema/数据库/授权材料条件；观测平台离线不导致业务不可用。慢查询和重试有总期限，数据库连接不可用时不在内存中宣称操作已接收。P4/P5 将总期限覆盖发现、调用及清理；网络超时后保留未知结果。按角色限制超时，避免把迁移和普通查询强套同一值。[PG 超时说明](https://www.postgresql.org/docs/current/runtime-config-client.html)

**验收：** 耗尽连接池、持锁不放、断数据库连接、下游持续慢速发送，以及发出后停机，分别得到有界等待/不就绪/结果未知；停止领取后已提交记录仍可恢复。基础指标覆盖池等待、租约过期、最旧待对账、outbox 积压和同步滞后，不能等 Langfuse 上线才发现积压。P1b 新增 `tests/test_service_lifecycle.py`，P4/P5 传输测试扩展，P9 验实际服务管理环境。

### D1-07 恢复数据库不等于恢复授权与业务现实：架构缺口，P1b/P3/P4/P9

**证据与影响：** 当前测试验证应用重启、事务回滚、回执断连，没有恢复旧备份或 PG 故障切换。若恢复点早于已发生的远端写入、nonce 消费或撤权，本地可能看起来“未执行/仍获授权”，即使数据库本身一致。异步复制也不能默认承诺零丢失。[PG 备份与时间点恢复](https://www.postgresql.org/docs/current/continuous-archiving.html)、[复制与故障切换](https://www.postgresql.org/docs/current/warm-standby.html)

**调整：** P1b 先做单实例备份/恢复和核对清单；P3/P4 加恢复后的写入冻结、授权状态核对与未知操作对账。恢复前隔离旧写入者；恢复后对照可信授权检查点、撤销状态、源回执和签名证据检查缺口，无法证明当前有效性的旧授权不得继续写入。恢复代次必须由不随该备份回滚的可信控制面或明确重新授权建立，不能在同一份回滚库中写个标记就宣称防重放恢复。P9 再验 WAL/PITR、主备切换、旧主隔离、外部证据/密钥配置恢复和业务认可的 RPO/RTO。

**验收：** 在动作成功与撤权后恢复到更早备份，服务不会自动重发或恢复旧权限；已知操作沿用原 ID 查询，缺失操作有源/证据核对路径；旧主/旧 Worker 不能继续产生新写入。恢复签名材料不会使已撤销授权重新有效。基础恢复使用 `tests/test_backup_restore.py`，跨系统用部署恢复/OWP 远端测试。没有企业目标时记录实测时间和数据窗口，不杜撰可用性承诺。

### D1-08 证据文件与知识负载：存储和运维缺口，P0/P3/P4/P7/P9

**证据与影响：** 目标架构把原文和证据包放文件/对象存储，但尚无发布完整性、恢复清单、清理约束或配额实现。PG 与 pgvector 初期共库，导入、建索引和历史增长可能争用核心事务资源。只限制 SQL 连接数不能保证 CPU/IO 隔离。

**调整：** P0 固定依赖来源、扩展版本与恢复所需组件；P3/P4 定义文件暂存→完整性核验→可用引用的发布流程及 PG 投递记录。失败时允许可清理孤儿文件，不允许把缺失/损坏证据宣称为已验证。保存可信密钥版本/公钥与验证政策，秘密不进入证据/trace；轮换不等于撤销历史可信签名。文件访问、备份和保留策略同受租户约束。P7 独立限制导入、embedding 与索引构建并发、批量和内存；保护授权/回执连接容量；监测磁盘/WAL、长事务、清理积压。实测仍干扰核心时再拆独立 PG 实例，不先加 Redis、Kafka 或图数据库。[pgvector 索引建设说明](https://github.com/pgvector/pgvector#hnsw)

**验收：** 文件上传中断、文件已落但 PG 失败、PG 引用存在但文件丢失/损坏，都得到可恢复且诚实的状态；重复投递只产生一个逻辑证据引用；清理不删除仍被发布/任务引用的证据。索引重建同时运行任务与回执，测量核心延迟和积压，达到预先配置的资源界限时限流/暂停非关键任务。磁盘不足不得返回虚假成功；备份恢复包含原文/签名证据和定位关系。验收进入证据、pgvector 和部署恢复测试。

## 3. 第二层：数据与 Ontology 深入审查

### D2-01 版本化语义需固定值的解释，P1a/P1b/P2a

**证据：** Registry 只定义基本字段类型，`storage.encode` 定义当前 JSON 摘要；没有单位/小数/时区或跨版本转换契约。

**调整：** 明确缺失与 null、精确小数与浮点、单位、时间点与时区、枚举及关系方向的表示；表达式必须类型检查和有界执行。新规范带版本，旧批准保留原字节/摘要，PG JSONB 用作查询表示，不把它的重新序列化当作历史签名原文。破坏性变更先做数据适配与影响检查，不能原地改变旧版本含义。

**验收：** 两个源对相同量的不同单位能按指定转换一致解释；非法混算拒绝；跨时区/空值不被误判等价；迁移前后旧摘要不变；同名规则换单位或枚举含义不能沿用旧批准。对应本体、迁移和发布测试。属于待建设契约，不是声称现有代码已经发生摘要失真。

### D2-02 同步必须识别源重建与断档，P2b

**证据：** 当前对象维护没有源游标；前次设计已有重复/乱序，但还需约定游标失效和源版本重置。

**调整：** 在来源契约中加入源代次/快照批次、可比较版本范围和完整性标记。增量游标到期、源库重建或序号重置时，停止宣称完整，进入受控重新快照；快照未完成或受权限限制，不把“未看到对象”当作删除。映射重做保留稳定规范 ID 和旧来源关联。

**验收：** 在相同源 ID 下重置序号、使游标过期、快照中途掉线、快照期间发生写入，均能识别断档并恢复；未完成快照不生成大批假删除；再同步不重复创建规范对象或混用两个源代次。对应 `tests/test_fact_sync.py`。

### D2-03 “我能看到的全部”不能冒充业务上的全部，P2a/P2b/P3

**证据：** 当前 `_ground` 直接取配置关联；目标语义查询将过滤对象/字段/边。若将过滤后的集合用于“所有成员满足”判断，会混淆可见范围与事实完整范围。

**调整：** 规则声明其所需全集与完整性条件。用户查询只返回获准集合；需要更大范围的规则只能由明确授权的服务判断，并输出调用者可见的决定/解释，不能把隐藏成员数量泄漏给用户。没有该服务权限或完整数据则返回依据不足。读取集绑定集合边界和来源完整性，不只绑定显示结果。

**验收：** 同租户有一个用户不可见且不满足条件的成员时，不能因可见成员全部满足就批准动作；也不向该用户泄漏隐藏成员身份或受保护计数。无完整性证明时拒绝否定性断言。对应语义查询、规则和 OWP 绑定测试。

### D2-04 删除、留存与派生数据需闭环，P2b/P7/P9

**证据：** 当前知识保留历史正文，尚无删除生命周期；新方案同时需要审计证据留存和索引/记忆撤回。

**调整：** 区分不可再用于运行、限权审计留存、到期物理清理三种状态。事实、历史、块、向量、缓存、记忆、产物和证据引用传播失效；备份中的保留按明确期限管理，恢复后先重新应用撤回/删除记录再开放查询。摘要也需访问控制，不把它当匿名数据。需要保留的证据与应删除正文分别处理，不以“审计”无限期保留全部内容。

**验收：** 用户撤回后，即使索引消费者延迟仍不能检索/执行引用旧内容；恢复旧备份不会重新公开删除记录；合法保留的历史效果可核对但不可被普通查询读取；到期清理有可核对结果。对应事实同步、权限检索、记忆及恢复测试。

## 4. 第三层：模型深入审查

### D3-01 路由标签不构成可复现模型发布，P2a/P5/P7

**证据：** `gateway._Route` 有 version/tags，但 `Registry.definition` 不包含完整网关配置；返回结果的模型名也不能证明供应商模型内容未变。

**调整：** 发布记录模型/endpoint 身份、配置摘要、输出契约、提示、数据处理范围与获准回退；供应商动态别名只能标注实际可追溯程度，不宣传完全可复现。embedding 模型/预处理/维度独立固定，禁止回退到另一向量空间混写。

**验收：** 同名路由改 endpoint、允许数据或输出契约后，旧任务不能静默换目标；合法固定旧发布可运行，实时禁用仍优先。模型别名变化被记录而非伪造精确版本。对应发布、模型后端和向量测试。

### D3-02 实际尝试与总期限必须贯穿回退，P5/P6

**证据：** Runtime 每次 `model.propose` 记一次 started，而网关内部可调用主/备两次；失败和失去租约的结果不会形成完整 completed 用量。

**调整：** 每次供应商请求有 attempt_id、路由、预留和用量状态；失败/取消/迟到仍记录已发生的请求。重试与回退共享截止时间及预算；供应商未报告消耗则保持待核对，不当零也不重复全额释放。继续把单次逻辑调用预算与实际成本预算分开。

**验收：** 主失败备成功记录两次实际调用；租约丢失后供应商返回的费用仍可核对；总期限到期不再启动回退；两个并发子任务不能重复花费同一余额。对应模型后端/图运行测试。

### D3-03 有效证据 ID 不等于结论被证据支持，P5/P7

**证据：** `model._validate_proposal` 和 Runtime 校验候选动作、理由长度及知识 ID 成员资格，没有验证理由与文档是否相符。

**调整：** 保留确定性范围校验；事实条件和执行许可由本体规则/OWP 决定。评测增加“引用真实但不支持结论”、缺证据、互相矛盾和工具返回注入。模型评审仅辅助评估文本质量，不让它成为授权决策器。检索质量、事实正确性、执行安全分别报告。

**验收：** 模型引用合法 ID 却提出不满足规则的动作仍无法执行；材料中的扩权指令无法改变范围；固定集分别报告引用正确与内容支持情况，需人工评判项保留人工结果。对应模型后端与 evaluation 测试/评测。

## 5. 第四层：Runtime 与安全深入审查

### D4-01 nonce、重试与授权期限需要独立状态机，P3/P4

**证据：** 当前已有 operation_id 和 unknown/not_found 语义；尚未接 OWP nonce。若简单“调用前消费 nonce、错误后再消费”，会使合法恢复失效；若超时就退回 nonce，又可能允许重放。

**调整：** 授权、操作登记与 nonce 消费采用原子绑定，记录稳定动作/请求摘要和允许的派发/结果状态。重启返回既有状态；结果未知仅按受限对账身份查证。确需再派发时同时满足原操作幂等与当前有效授权；授权已过期需新授权引用，但保持业务操作 ID 和参数绑定，不能凭新 nonce 变成第二个效果。如何更新源侧授权元数据需在连接器契约明确，不改旧业务请求身份。

**验收：** nonce 消费后尚未派发就崩溃、派发后失去响应、授权在等待期间过期、两个进程重复提交，均有明确恢复路径；过期不能新写，但可查既有结果；同 nonce 不能绑定别的操作。对应 OWP profile、安全入口和远端闭环测试。

### D4-02 本地“事务工具”必须约束副作用范围，P1a/P4/P9

**证据：** `tools.register` 接受 callable，`list_tools` 将非 remote 标记为 transactional。当前测试只证明 handler 对同一 SQLite 连接的修改可回滚，无法使文件、邮件或网络请求随数据库回滚。

**调整：** 明确本地事务工具仅允许对同一框架事务做约定数据库修改；文件/进程/外部网络效果转入有操作记录的外部执行路径。P4 注册说明、适配测试和环境最小化；P9 才证明恶意代码无法绕过。不能以 handler 的声明代替真实原子性或隔离。

**验收：** 同库 handler 抛错时对象/回执全部回滚；带网络/文件外部效果的适配不能被登记为具备数据库原子回滚保证；生产隔离用实际访问尝试验证。分别归通用工具、执行隔离套件。

### D4-03 对账与证据补发也需要持久调度边界，P4/P6/P9

**证据：** 当前 `work` 顺序扫描前若干任务，`reconcile` 按调用查询；无 next_attempt_at、退避、租约或长期未决处理机制。手动可恢复不等于后台能持续恢复。

**调整：** 在 PG 记录下次查询时间、有界退避、最近错误和领取状态，按工具/租户限流；未知业务结果不因次数耗尽变成“未执行”。长期未决进入人工核对状态且保留查询能力。证据 outbox 独立重试，消费者幂等；不需要先上消息中间件。P6/P9 更换调度器时保留同一操作和单一重试责任方。

**验收：** 一个源持续失败不饿死其他任务；进程在投递前后崩溃可补发且不重做效果；对账服务撤销写权限后仍按受限身份查询；重试间隔及上限可观察，长期未知不会自动重发。归远端闭环、服务生命周期和图恢复测试。

## 6. 第五层：AI 应用深入审查

### D5-01 历史任务查询依赖现行配置，P2a/P8

**证据：** `api.dispatch` 47–54 行在 GET 任务之前调用当前 `registry.definition`；应用删除或定义不可用会导致请求失败。`Runtime.inspect` 本身只读持久记录。该路径是源码确认的恢复可用性问题，本轮未新增运行复现用例。

**调整：** 任务查看权限依据持久任务身份/发布与当前资源权限判断，不依赖当前应用仍在配置中。历史查看与继续执行分开；旧发布被禁用可阻止新执行，但不应阻止获授权的查询/对账/证据导出。

**验收：** 提交后删除现行应用配置或发布新版本，合法请求者仍能查看旧任务与回执；无查看权者依然拒绝；旧动作没有有效发布/当前许可时不能执行。进入发布与 `tests/test_console_api.py`，保留现有 API 回归。

### D5-02 审批和客户端重试缺少一致反馈契约，P1a/P2a/P8

**证据：** 当前 submit 有请求键；`decide` 仅接受 awaiting_approval，再次相同决定会报错。浏览器超时后不能仅据重试报错判断原审批是否生效。未来多动作任务更需要精确绑定。

**调整：** 审批决定携带稳定请求标识和提议版本/摘要；同标识同决定返回已记录结果，相反决定或不同提议拒绝。任务进度、业务效果、证据验证和人工接受分别展示，取消不能表示撤销已发生效果。

**验收：** 审批提交成功但响应丢失后重试，不产生第二条矛盾决定；过期页面不能审批新提议；并发同意/拒绝有单一确定记录；已发出取消仍明确显示待对账。归通用契约、身份/发布和 API/UI 测试。

### D5-03 任务事件与证据导出需要边界，P2a/P8

**证据：** `Runtime.inspect` 433 行起一次性返回全部事件及原始远端 payload/response，当前 API 只有任务角色检查。未来长期运行、多动作与敏感回执会放大响应和可见数据。

**调整：** 明确分页、稳定游标和响应上限；审计原始材料与应用展示投影分开，字段/关系/证据过滤同语义权限。PG 自增分配顺序不等于提交顺序，游标不能简单跳过所有较小但尚未提交的 ID。首版按任务串行分配事件修订并提交，或采用可证明不漏事件的已提交水位与去重方案；不把序列空洞解释为数据丢失。断线续传沿同一持久事件契约恢复。

**验收：** 大量事件分批读取无重复/漏读已提交事件；故意制造“较小 ID 晚提交”仍不丢事件，游标不能跨租户复用；受限字段不经原始回执、错误、导出泄漏；撤权后的下一页立即受限。归语义查询与 API/SDK 测试。

## 7. 第六层：业务接入深入审查

### D6-01 幂等有保留期限，查询身份也可能变化，P1a/P4/P9

**证据：** `idempotent=true` 只有布尔声明；测试源持久保存全部操作，尚未模拟下游去重记录过期。`adapter_for` 要求原目的地仍匹配，变更后缺少受控旧操作查询迁移。

**调整：** 连接器声明幂等键作用域、保留窗口、查询可用期、同键异参数行为和源身份。超过可证明窗口不得自动重发；保留旧操作对应的受限查询连接，源地址迁移须验证身份/回执连续性，不把新目的地自动视为原源。查询凭据可轮换但不能扩权。

**验收：** 已成功操作的源去重记录被清理，再次 not_found 仍不能重发；源地址/身份变更不误对账；写权限撤销后按获准查询身份仍可核对原操作。归远端运行/OWP 闭环，P9 独立源查询验证。

### D6-02 MCP 工具名相同不证明语义相同，P4

**证据：** `_discover_tools` 主要检查 execute/lookup 名称存在；适配 identity 包含 endpoint/工具名，未绑定服务发现中的输入输出定义。当前属于受信配置的协议子集，并非完整 MCP SDK 接入。

**调整：** SDK 发现与框架工具发布分开；登记受支持协议、输入输出 Schema 摘要、动作类别及允许能力。发现到工具不自动开放；同名 Schema 或语义版本改变必须重新校验/发布。MCP 会话 ID 与传输认证不能代替 OWP 动作授权。

**验收：** 同名工具换参数/结果 Schema 时旧动作拒绝调用；未知工具不开放；协议不兼容明确失败；会话终止失败不得覆盖已确认的业务结果。归 MCP SDK 和 OWP 远端测试。

### D6-03 回流核对不能假设版本始终加一，P1a/P2b/P4

**证据：** `remote_execution.valid_response` 接受成功结果的条件包括源版本等于 expected_version + 1；适合当前合成状态变更，不适合不透明 ETag、多对象或异步批处理源。

**调整：** 通用回执明确源版本令牌、变更对象集合、完成状态和可独立查询依据；版本比较由已登记源契约决定，框架本地修订号与源版本分开。旧动作继续使用原 +1 契约。异步受理不是业务成功，回流缺关联或与回执冲突进入核对，不按时间最近自动覆盖。

**验收：** 不透明版本源、跨多次修改的版本跳跃、受理后失败、多对象部分成功，以及同步事件先于回执到达，均有正确状态和一次效果关联；原有单对象 +1 用例保持通过。归通用契约、事实同步和远端回执测试。

## 8. 对开发计划的约束与关闭条件

开发计划新增第 6 节，逐项引用 D1–D6 并安排阶段。这里的详细验收与该阶段原验收同时适用；不以引入更多组件替代行为保证。

第一层的最小退出条件：P0/P1b 的依赖、迁移、并发、连接上限、领取、单实例恢复及基础运行监测成立；P2a/P3 的租户和授权跨层接口有实测。此时可进入本地集成，不宣称完成 P9 企业隔离/高可用。P9 的部署目标、身份、密钥服务与下游接口需接入方提供，本轮不虚构这些输入。

六层均已完成本轮源码/设计深入核对，但 24 项的实现和新增验收均未完成。只有 D1-01 的告警定位完成；修复仍待开发。后续实施时按每项指定用例更新结果、环境和证据，不能因为文档已补而关闭问题。
